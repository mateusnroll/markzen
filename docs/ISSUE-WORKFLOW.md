# GitHub requirements and issue delivery

GitHub issues in [mateusnroll/markzen](https://github.com/mateusnroll/markzen/issues) are the product backlog and the source of future product requirements. Numbered specifications in `docs/specs/` are versioned technical contracts; ADRs explain implemented architecture. Do not maintain another backlog in Git or use a spec's Non-goals as an implicit delivery queue.

## Requirements and readiness

Each issue states its problem, users, outcome, stable `PRD-R-001` requirement IDs, observable acceptance intent, dependencies, affected specifications, non-goals, product decisions, technical questions, proof expectations, and completion conditions. IDs are scoped to the issue and never renumbered after review. Split outcomes that can be delivered or fail independently. A planning or release issue identifies its documentation or external acceptance deliverable instead of promising an implementation PR can complete it.

Product requirements describe success and applicable failure, cancellation, concurrency, recovery, accessibility, privacy/security, platform, and bounded performance behavior. Reuse existing contracts by exact reference rather than duplicating their prose. Technical questions distinguish discoverable facts, ordinary implementation choices, and product or architecture decisions requiring the human. Agents research facts and resolve routine technical choices within the approved product; they never invent material product decisions.

An issue's requirements state is **Draft**, **Ready**, or **Delivered**. Draft requirements can contain proposed choices and blocking questions. Ready requires complete product decisions, explicit acceptance intent and exclusions, and human approval with source provenance and a digest of the exact requirements snapshot. Priority (**Next**, **Planned**, or **Later**) is independent of readiness. Both fields live in the issue; issue numbers are not an execution order. Technical specification approval remains a separate independent gate. Delivered records the merged PR and verified acceptance; an open or green PR alone is insufficient.

Record product approval separately from the frozen requirements payload. Snapshot the title, body, relevant decisions/comments and provenance outside Git, then hash the exact UTF-8 snapshot bytes with SHA-256. Approval metadata and subsequent handoffs are separate records so adding them does not change the approved payload. On resume compare normative content, not merely `updated_at`: a handoff does not expand scope, while a changed requirement invalidates the relevant approval. A label, agent summary, third-party comment, or historical approval of different bytes cannot grant authority.

## Discovery and authorization

`$implement #N` or an explicit request to implement an issue starts discovery and, once its requirements and concrete scope are settled, the authorized issue-to-PR run. Read `CLAUDE.md`, the spec process, this workflow, the live issue and comments, dependency PRs, and any existing branch/PR/evidence. Reuse decisions and authorization from the human's current or recorded approved scope. Gather foreseeable questions together with recommendations before implementation. Do not ask routine stage confirmations after scope authorization.

An implementation request covers that issue's local branch/worktree, requirements/spec drafting, installed specification and OCR reviews within their current bounds, dependency installation in the project, verification, commits, one PR, and the bounded CI repair below. Record the actual repository, base, checkout, artifact path, reviewer stages/bounds and exclusions before paid execution; ask only for authority not already provided or a changed material boundary. A bare issue reference or “what's next?” authorizes read-only discovery and interviewing, not paid construction. Select the next work through the live delivery plan below.

Merge, deployment, signing, release publication, billing/provider setup, authentication changes, force-push, repository administration and the next issue require their own authorization. Release issues prepare reviewable code/runbooks before any outstanding external approval. A Ready issue cannot authorize these actions by itself.

## Answering “what's next?”

[Delivery plan #52](https://github.com/mateusnroll/markzen/issues/52) owns the explicit execution order, stage completion evidence and milestone proposal. It is coordination metadata, never a product implementation target. Keep the queue on GitHub; milestones group work but do not determine its order.

1. Read the live plan, referenced issues and relevant comments, approval provenance, prerequisites, linked PRs and acceptance evidence. Reconcile the plan's bootstrap gate and active worktree/run handoffs first; preserve active ownership and consumed review budgets.
2. Select the lowest unfinished stage in the plan's explicit order. Verify completion against that stage's evidence: issue closure, a local Implemented spec or a green unmerged PR is insufficient. Preparation stages can finish while their release issue stays open; later publication stages require actual external acceptance. A missing future technical spec is work to do inside the issue workflow, not a reason to skip the issue.
3. Report that issue and stage, why it is next and its earliest incomplete gate. An active PR needs review/merge before the successor; a blocked stage needs its concrete blocker resolved. Do not silently skip it. Explicit human selection of another issue takes precedence without expanding its scope or authorization.
4. If ranks are ambiguous, a new issue is unplaced, a dependency contradicts the queue, a listed issue was withdrawn or approval changed, report the precise planning conflict before selecting new implementation work. Do not infer order from issue numbers, dates or priority ties. Intentionally deferred Draft discussions remain outside the executable queue.

This answer is discovery only. It does not start implementation, merge a PR, authorize paid reviews or advance external release gates. When no implementation remains, identify the pending external stage or deferred discussion from the plan.

## One issue, one PR

1. **Reconcile and isolate.** Fetch `origin/main`, verify dependency PR merges and any external acceptance, and record the full base SHA. Reuse a suitable task-owned managed worktree; create one when isolation is needed. Start a new `codex/issue-N-description` branch from current main or resume the issue's recorded branch/PR. Preserve unrelated changes and detect an active writer before taking ownership. Reconcile ambiguous external operations before retrying.
2. **Freeze requirements.** Preserve the approved requirements snapshot and approval provenance. Use a task-owned external directory, conventionally `~/.local/state/codex/markzen/issue-N/<run-id>/`, for the run ledger, immutable inputs, reviewer outputs, logs and screenshots. Recover an existing Automode run and its budgets when one owns the issue; do not replace its ledger or rerun completed stages.
3. **Specify.** Use `$spec` to draft the next available numbered technical contract, trace every issue requirement, identify implementation ripples and amend affected contracts. Resolve the independent Draft simplicity review. Invoke installed `$spec-approver` with its official runner, pinned base, complete candidate/change set and requirement projection. Verify its official receipt, distinct reviewer identity and exact digests before recording approval. Preserve installed models, policies, validators and retry limits; an unfavorable verdict is not an infrastructure retry.
4. **Implement locally.** Invoke `$implement` in its local phase. Write primary AC-named tests first and prove the intended missing behavior fails, implement the smallest approved solution, run required verification and independent implementation simplicity review, record necessary ADRs and complete the index lifecycle. For UI work inspect actual browser/Electron journeys and accessibility states. Fakes do not prove native integration.
5. **Review the checkpoint.** Commit the complete verified tree and use installed `$ocr-pr-review` on the pinned base through the clean checkpoint with the approved contract as background. Require an officially validated `ready_for_pr` receipt. Preserve the checkpoint, permitted remediation commit and final SHA; do not amend history or change source after review without revalidating it.
6. **Publish.** Use `$pull-request` in reviewed-checkpoint mode to push exactly the OCR final SHA and create/update the issue's one focused ready PR to `main`. Include issue/requirement/spec links, approved digests, verification, the active `code-review.md` verbatim, and an inspected screenshot uploaded directly to GitHub for user-visible interface changes. Attach the PR to the current Codex chat. Leave it unmerged.
7. **Check CI.** Bind observations to the current full PR head. Require `verify` and all three declared `shell` jobs, plus any newly approved mandatory checks. Performance reporting remains advisory under current specs. An empty branch-protection required-check list is not green CI. Check mergeability against live main immediately before claiming readiness.
8. **Hand off.** Record the branch/base/head, PR, current approvals/receipts, local verification, exact-head CI, consumed review budgets and next gate in the issue. Include its stable delivery-plan stage and scoped completion evidence when preparation and external acceptance are separate; a preparation PR does not complete publication. Stop after delivering this issue; do not start its successor automatically. Use `Closes #N` only when merge completes all scoped acceptance; otherwise use `Refs #N` and keep external gates visible.

An issue may contain several sequential technical slices when each is necessary to its approved scope. Plan and authorize the review scopes up front, retain each slice's exact evidence, and require a final review of the complete issue diff. Additional slices are not a way to reset an exhausted review or CI budget. Prefer one bounded spec when it can prove the whole issue.

## Bounded repair and recovery

Keep the installed spec-approver's one remediation/follow-up lifecycle and OCR's adjudication/remediation bounds unchanged. For CI, investigate logs before classifying a failure. Rerun infrastructure-failed jobs at most once. For an implementation-caused failure, allow one repair cycle: fix within the approved contract, run complete required verification and commit a replacement checkpoint. Before paid execution the caller must have explicitly scoped two distinct OCR stages: the initial clean checkpoint and at most one superseding cumulative CI-replacement checkpoint. The replacement uses its own new immutable range/receipt, never reruns the initial stage, and cannot retry an unresolved/exhausted initial finding. Preserve both receipts and their supersession relationship, push only the replacement's validated final SHA, and wait for exact-head CI again. No stage runs a second broad cycle, and no second CI code-repair stage is allowed. If the installed reviewer cannot support this separately authorized caller stage under its current contract, preserve the repair and hand off rather than alter its policy or claim the old receipt covers new code. Ambiguous causes require investigation or a precise handoff.

If main moves, reconcile before merging it or rebasing: changed code or ranges need affected proofs and review evidence within existing bounds. Never call old-head evidence current. Missing capabilities, new material decisions, invalid/missing receipts, disputed or exhausted findings, and an unprovable reviewed/tested head halt dependent work. Preserve progress and report the earliest incomplete gate, exact blocker, available evidence and one concrete resume action.

Keep a compact manifest with the issue, run ID, base/checkpoint/final SHAs, branch/PR, input hashes and approval sources, official receipt paths/hashes, review scopes and consumed attempts, verification logs, CI URLs, external effects and current handoff. Preserve complete tool-produced review directories and superseded receipts outside Git. Public issue/PR handoffs expose only reviewed, non-sensitive summaries and links. Markzen is public: do not copy Tactile's private draft-release archive policy, upload private review inputs without authorization, or make expiring Actions artifacts the sole durable evidence. A local-only archive must be identified as local-only, with a concrete retrieval path and any portability limitation.

Documentation-only workflow changes use applicable document consistency checks and skill forward-testing; they do not invent runtime or OCR evidence. Product-code changes retain the normal spec, runtime, verification and independent-review gates. A regression fix preserving an existing approved contract may reuse that contract with explicit regression mapping; any behavior change requires a reviewed amendment first.
